# Prototype: the causal-chain milestone

This is a minimal, runnable proof of the milestone described in the
project brief (Section 二十三 / the "first real milestone" section):

```
Day 1:  Agent has belief A
        ↓
        Episode #18 happens
        ↓
        Memory #7 forms
        ↓
        Later Episode #31 conflicts with it
        ↓
        Interpretation changes
        ↓
        Belief A weakens
        ↓
        Behavior changes
        ↓
Day 14: Agent behaves differently
        ↓
        User asks: "Why are you different now?"
        ↓
        System shows the causal history.
```

It is **not** the product described in the rest of the brief (no /people,
no /talk, no real conversational AI, no polished UI) and it is **not** an
architecture recommendation — see the disclaimers below. Its only job is
to prove the causal chain is real: every explanation `/api/explain`
returns is computed by walking actual rows this script created, not
hand-written output.

## What it demonstrates concretely

- A belief (`trust_followthrough`) is seeded on "Day 1" with real
  supporting evidence (a genesis episode), not asserted from nowhere.
- A single, ambiguous negative episode on "Day 5–7" is correctly treated
  as insufficient evidence and changes nothing — `PROJECT_CONSTITUTION.md`
  Section 8 (weak/provisional evidence must not drive behavior) in
  action.
- A second, clearer episode on "Day 10" is directionally consistent with
  the first, and their combined evidence crosses the "accumulated
  evidence" bar from Section 6 — the belief weakens (0.8 → 0.4), and this
  is recorded as a `change_event` with explicit provenance (which
  episodes, which memories, which interpretations).
- The belief change causes a behavior change (`reminder_frequency`
  low → high), itself a separate, linked `change_event`.
- On "Day 14," asking the running system "为什么你最近老是提醒我确认事情？"
  (or hitting `/api/explain?key=reminder_frequency` directly) produces a
  real explanation, generated by traversing the provenance chain back to
  the two actual episodes — not a canned answer.

## Running it

```bash
cd apps/prototype
npm run seed   # (re)builds data.sqlite and runs the Day1-14 scenario
npm start      # serves the API + frontend at http://localhost:3000
```

Requires Node.js >= 22.5 (uses the built-in, still-experimental
`node:sqlite` module — chosen specifically so this prototype has **zero
npm dependencies** and is guaranteed runnable without a network-dependent
`npm install`). No other setup, no Docker, no external database.

Pages: `/` (today + ask-it-why chat), `/history.html` (the causal
timeline — the most important page), `/self.html` (current beliefs and
behavioral tendencies), `/debug.html` (raw internal pipeline state, for
inspecting the full chain table by table).

## Explicit disclaimers — read before treating any of this as settled

- **Thresholds are placeholders, not validated numbers.**
  `SINGLE_EVENT_CONFIDENCE_THRESHOLD`, `ACCUMULATED_MIN_COUNT`, etc. in
  `pipeline.js` are illustrative constants chosen to make this specific
  demo scenario work. `PROJECT_CONSTITUTION.md` Section 6 explicitly
  says these should not be invented from theory alone — they still need
  real validation once there's real usage data. Do not copy these numbers
  into a real implementation without re-deriving them.
- **Interpretation is hand-authored, not generated.** A real system
  (per `docs/episode-model.md` and the deferred Phase 2–5 docs) would
  likely use an LLM to segment episodes, judge salience, and generate
  interpretation text. This prototype hard-codes interpretation
  statements in `seed.js` to keep the demo deterministic and
  dependency-free. The pipeline functions (`interpret`,
  `evaluateBeliefUpdate`, etc.) are written so an LLM-backed
  implementation could be substituted behind the same interfaces later.
- **The Memory layer is reduced to three fields** (fidelity,
  accessibility, confidence) instead of the fuller Fidelity/Accessibility/
  Influence/Confidence/Provenance set the brief describes. This is a
  scope cut for the prototype, not a decision that the fuller model is
  unnecessary.
- **SQLite via `node:sqlite` is a prototype convenience**, not a
  recommendation for the real system's storage layer.
- **Phase 2–6 (`docs/memory-model.md`, `forgetting.md`, `activation.md`,
  `interpretation-model.md`, `self-model.md`, `relationship-model.md`)
  were not written before this was built** — per the project owner's
  explicit direction to skip ahead and prove the milestone first. The
  logic here should be treated as a working sketch to be reconciled with
  those documents when/if they're written, not as having already
  answered their questions.
